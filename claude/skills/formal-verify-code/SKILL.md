対象コードの実装から振る舞いをモデル化し、複数の形式検証ツールで並列に検証して、結果を1つのHTMLに統合してください。

引数: $ARGUMENTS

環境確認:

- leanコマンドの有無: !`type lean || true`
- quintコマンドの有無: !`type quint || true`
- alloyコマンドの有無: !`type alloy || true`
- alloy6コマンドの有無: !`type alloy6 || true`
- python3コマンドの有無: !`type python3 || true`
- uvコマンドの有無: !`type uv || true`
- nixコマンドの有無: !`type nix || true`

各ツールの検証手順は以下のファイルに定義されている。サブエージェントに読ませる。

| ツール | 手順 | 出力するモデルファイル |
|---|---|---|
| lean | `${CLAUDE_SKILL_DIR}/tools/lean.md` | `.lean` |
| quint | `${CLAUDE_SKILL_DIR}/tools/quint.md` | `.qnt` |
| alloy | `${CLAUDE_SKILL_DIR}/tools/alloy.md` | `.als` |
| z3 | `${CLAUDE_SKILL_DIR}/tools/z3.md` | `.py` |

## 大原則

- 対象コードは変更しない
- コメント・ドキュメント・テスト・README は参照しない。実行されるコードだけを根拠にする（コメントと実装が食い違っていても、実装を真とするため）

## モード

引数に `quick` または `thorough` があればそのモードで実行する。なければ手順2の確認でモードも選ばせる（推奨は quick）。

| モード | 目的 | 時間 |
|---|---|---|
| quick | 主要な欠陥を素早く見つける。検証範囲は狭くてよい | 全体で5〜10分以内 |
| thorough | 時間をかけて広い範囲を網羅的に検証する | 全体で最大1時間 |

各ツールのモード別の設定は `tools/*.md` の「モード別設定」に定義されている。

quick の共通ルール:

- サブエージェントごとに実行時間の予算を約8分とし、個々の検証コマンドには `timeout` を付ける
- 予算内に終わらない検証項目は縮小（範囲・ステップ数・スコープ）して再実行し、それでも終わらなければ「未検証」として理由を報告する
- 検証範囲を狭めた項目は、結果が網羅的でないことを明記する

thorough の共通ルール:

- サブエージェントごとの実行時間の予算を最大50分とし、個々の検証コマンドには残り時間を超えない `timeout` を付ける
- 予算内で各ツールが可能な最も網羅的な検証を行う
- 有界検査は範囲を段階的に広げ、反例が出ない最大の範囲まで確認する。予算が尽きたらそれ以上広げず、到達した範囲を報告する
- 長時間かかる検証コマンドはバックグラウンドで実行し、完了を待つ。予算内に終わらないものは打ち切り「未検証」として理由を報告する

## 1. 対象コードの整理

引数のパス（ファイル・ディレクトリ・関数名）を対象とする。指定がなければ AskUserQuestion で確認する。

対象コードを読み、以下を抽出して ID を付与する。全ツールで共通して使う。

- `C1, C2, ...`: モデル化するコード要素（状態・データ構造・関数/操作・並行実行単位）。`file:line` を併記する
- `P1, P2, ...`: 検証する性質。根拠となるコード箇所（`file:line`）を併記する
    - 明示的なもの: assert、型・契約、例外・エラー処理、入力検証の分岐
    - 暗黙的なもの: 識別子名や使われ方から推定される意図（例: 残高が負にならない）
    - 汎用的なもの: 実行時エラー（範囲外アクセス、ゼロ除算、オーバーフロー、null 参照）、デッドロック、競合、到達不能な処理、終了しない処理

あわせて以下を決める。

- 抽象化方針: 外部I/O・ライブラリ呼び出しの扱い、整数幅、コレクションの有界化、並行性の粒度
- 意図が判別できない点（バグか仕様か）の洗い出し

## 2. ツール選定

引数に `lean` `quint` `alloy` `z3` があればそのツールだけを、`all` なら4つすべてを実行し、選定は行わない。

引数がなければ、コードの特徴から実行するツールを選ぶ。

- 状態遷移・並行処理がない（純粋な関数やデータ構造だけ）: Quint は不要
- 算術がない（関係・集合・参照だけ）: Z3 は不要（Alloy と重複する）
- 関係構造がなく数値・分岐条件が中心: Alloy は不要（整数の扱いが弱い）
- 状態空間が小さく有限: Lean は不要（有界検査で網羅できる）
- 再帰・任意長のデータ・任意の N での正しさが重要: Lean が必要

選定結果と除外理由、C/P の一覧、抽象化方針、意図の曖昧点を AskUserQuestion でまとめて1回で確認する。モードが未指定ならここで合わせて確認する。ユーザーはここでツールや性質を変更できる。決定事項は一覧化して以降に引き継ぐ。

## 3. 並列検証

選定したツールの数だけ general-purpose サブエージェントを1メッセージで同時に起動する。各プロンプトには以下を含める。

- 対象コードのパス、C/P 表、抽象化方針、意図の曖昧点の決定事項、環境確認の結果
- 実行モード（quick / thorough）と、上記「モード」の該当する共通ルール
- 上表の該当ファイルを読み、その手順に従う指示
- 以下の上書き指示
    - ユーザーへの確認はしない。残った曖昧点は仮定として記録して進める
    - 対象コードを変更しない。コメント・ドキュメント・テストを根拠にしない
    - HTML は出力しない。モデルファイルのみカレントディレクトリに出力する
    - 最終報告を以下の構造で返す
        - ツールとバージョン、実行コマンド
        - モデルファイル名
        - コード要素（C）とモデル要素の対応
        - 抽象化による乖離（過大近似 / 過小近似、表現できなかった箇所）
        - 検証項目ごとの結果（性質の分類、対象の P、結果、網羅性と検証範囲）
            - 結果は 証明 / 成立 / 違反 / 未検証 / 表現不可 のいずれか
        - 反例（ID、内容、対象の P、コード上の実行経路（`file:line` の列）、解釈（どのような欠陥か））
        - 置いた仮定
        - コード修正案（修正自体は行わない）

## 4. 反例の確認

各反例を対象コードに照らして確度を判定する。

- 確定: コード上の実行経路をたどって再現できる。入力値や呼び出し順などの再現条件を示す
- 偽陽性の疑い: モデルの抽象化・近似が原因で、実コードでは起きない可能性がある。理由を示す

コードやテストの追加・実行による再現はしない。

## 5. 統合HTML

カレントディレクトリに以下の構成のHTMLファイル `formal-verify-code-report.html` を出力する。

- 要約
    - 主要なバグと推奨するコード修正案
- 性質 × ツール マトリクス
    - 行は P。根拠のコード箇所と関係する C を併記する
    - 性質の分類は充足可能性・不変条件・安全性・活性・デッドロック・到達性
    - 網羅的な結果と有界な結果を区別する
    - 実行しなかったツールは「対象外」とし、除外理由を書く
- モデルの構造
    - ツールごとに図解する
    - コード要素（C）とモデル要素の対応表、抽象化方針を記載する
    - ツールごとに表現できなかった、近似した点も併記する
- 意図の曖昧点
    - ツールごとに置いた仮定も併記する
- 反例・問題
    - ツール間の重複を統合し、検出したツールを併記する
    - 対象の P とコード上の実行経路（`file:line`）を併記する
    - 確度（確定 / 偽陽性の疑い）と解釈（どのような欠陥か）を併記する
    - コード修正案を差分形式で併記する（修正自体は行わない）
    - それぞれ図解する
- ツール間の食い違い
    - 食い違いの理由（表現力の差、有界性、モデル化の差）を考察する
- 検証範囲
    - 実行モード（quick / thorough）を冒頭に記載する
    - ツールごとに記載する
    - quick の場合は、thorough で追加で検証できる範囲も記載する

C や P や反例などをIDで示す場合、その内容もわかるようにする。（併記するか、マウスホバーで見れるようにする）
図解は以下の候補から適したものを1つまたは複数選択して行う。

- 状態遷移図
- ペトリネット
- オブジェクト図
- シーケンス図
- 依存関係グラフ
- コールグラフ
- フローチャート
- データフロー図
- トレース表
- 証明木
- 変数と制約の二部グラフ
- ガントチャート
