指定された言語を学ぶための演習プロジェクト（rustlings / exercism 形式）を、言語仕様の章立てに沿って生成してください。学習者がコードを書き、コマンド1つで合否がわかる状態にします。即時フィードバックが学習効率を左右するためです。

問題数が多くなるため、初回にシラバス（全章・全トピック）を作り、問題は章ごとに段階生成します。

引数が空の場合は言語を質問してください。

## 手順

1. 要件を確認する（未指定は既定値で進め、質問は言語が不明なときだけ）

    | 項目 | 既定値 |
    |------|--------|
    | 言語 | 必須 |
    | レベル | 他言語経験のある初学者 |
    | 範囲 | 言語コア＋標準ライブラリ |
    | 問題数 | 1章あたり5-12問（トピック数に応じる） |
    | 出力先 | `./<lang>-exercises` |

2. 生成対象を決める
    - 出力先に `SYLLABUS.md` がない: 初回。シラバス・共通基盤（`README.md`・`check.sh`）・第1章を生成する
    - ある: 引数の章、なければ未生成の最初の章だけを生成する。シラバスは原則変えず、誤りがあれば直して報告する

3. 言語の種類に応じて参照ファイルを読む
    - 汎用言語: `references/programming-languages.md`
    - 形式仕様/証明言語（Alloy・Quint・Lean・Dafny・Bend 2）: `references/formal-languages.md`
    - 記載のない言語は、同等の標準ツール（追加依存なしのテストランナーや検証器）を選ぶ

4. 処理系の有無を確認する: `type <command> || true`
    - なければ nix が使える場合は nix shell、使えない場合は公式の手順でインストールする

5. 一次資料を取得する（初回、および処理系のバージョンが `SYLLABUS.md` の記録と変わったとき）
    - 資料の版は時期で変わるため、実行時に取得する
    - WebSearch / WebFetch で、公式の言語仕様/リファレンスと標準ライブラリのドキュメントを探し、目次を取得する
    - インストール済み処理系のバージョンに対応する版を優先する。処理系が持つ組み込みのガイド（`bend guide` 等）があれば併用する
    - 見つからない・取得できない場合は、その旨と代替資料をユーザーに伝える

6. シラバスを設計する（初回のみ）
    - 取得した目次を網羅性の基準にする
    - 章 = 仕様の章/標準ライブラリのモジュール群。依存順（前の章の知識だけで解ける順）に並べ、コア→標準ライブラリの順にする
    - 各章をトピック（ID `CC.T`）に分解し、全トピックに最低1問を割り当てる
    - 対象外にするトピック（処理系依存・非推奨・FFI 等）は理由付きで明記し、黙って省かない
    - `SYLLABUS.md` に、資料名・URL・版（処理系バージョン）・取得日と、章・トピック・出典（仕様の節）・対応問題・生成状況の表を記録する
    - 1問1概念にする
    - 他言語の直訳ではなく、その言語固有の考え方や落とし穴を優先する（例: Rust の所有権、Alloy の過剰/過少制約、Quint の状態遷移と不変条件、Lean の帰納法、Dafny のループ不変条件）
    - 評価順序・境界値・暗黙変換・未定義/実装依存の挙動など、仕様の細部も問題にする
    - 章内では問題種別を交互に並べる（同種が続かないようにすると、種類の切り替えで記憶が定着しやすい）
    - 各章の最後に統合問題を1問置き、その章と過去の章の概念を組み合わせる（復習で記憶が定着するため）

7. 以下の構成で生成する

    ```
    <lang>-exercises/
      README.md              実行方法、章一覧と問題一覧（チェックボックスで進捗管理）
      SYLLABUS.md            網羅表（資料・章・トピック・出典・問題・生成状況）
      check.sh               ./check.sh CC-NN で1問、./check.sh CC で章全体、引数なしで生成済みの全問を採点
      exercises/CC-<chapter>/NN-<slug>/
        README.md            種別・学習目標・問題文・段階的ヒント（<details>）
        <雛形> + <テスト/検証対象>
      solutions/CC-<chapter>/NN-<slug>/
        <解答> + EXPLANATION.md（解説・よくある誤り・関連トピック）
    ```

    - 解答は学習者が誤って見ないよう `solutions/` に分ける
    - `check.sh` は初回に作り、以降の章でも修正なしで使える汎用的な形にする
    - `check.sh` には検証コマンドと抜け道の検出（`sorry` 等）を含める。警告付きで通る言語があり、合格判定を統一するため常に用意する
    - 雛形・解答のコメントは、その言語を知らない学習者向けに非自明な点だけ書く
    - ヒントは3段階程度で、最後でも答えそのものは書かない
    - 2章目以降は `README.md` と `SYLLABUS.md` の該当章の状態を更新する

8. 問題種別ごとに作る（3種別すべてを含める）

    | 種別 | 汎用言語 | 形式仕様/証明言語 |
    |------|----------|-------------------|
    | 実装 | シグネチャのみの雛形＋テスト | 空の本体・`sorry` を埋める、pred/アクション/不変条件を書く。用意した検証が通れば合格 |
    | バグ修正 | バグ1-2個入りコード＋テスト（バグ箇所は明示しない） | 過剰制約・過少制約・不変条件違反・通らない証明を直す |
    | リファクタリング | 非慣用的だが動くコード＋振る舞いを固定するテスト。解答に改善観点のチェックリスト | 冗長な仕様/証明の書き直し。旧定義との同値性を検証で保証 |

9. 生成後に自分で検証する（今回生成した章が対象）
    - `solutions/` の全問が合格する
    - `exercises/` の雛形では、実装・バグ修正が不合格、リファクタリングが合格になる（テストが意味を持つことの確認）
    - 解答で `sorry`・`assume`・`{:axiom}`・`{:verify false}`、検証対象を空にする等の抜け道を使っていない
    - `SYLLABUS.md` で、その章の全トピックに問題が割り当たっている
    - 失敗したら問題・採点を直して再実行する

10. 完了報告: 出力パス、生成した章の問題一覧（種別・トピック）、網羅状況（生成済み章/全章）、採点コマンド、検証で実行したコマンドと結果、次章の生成方法（`/language-exercises <lang> [章番号]`）を簡潔に伝える
