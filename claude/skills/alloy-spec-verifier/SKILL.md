# 仕様の Alloy 検証スキル

仕様を Alloy 6 でモデル化し、Alloy Analyzer（SAT ベースの有界モデル検査）で検証して、結果を仕様の言葉で報告します。

## このスキルのスコープ

### 含まれるもの
- ✅ 仕様からの構造・制約・操作・状態遷移の抽出とモデル化
- ✅ 充足可能性（矛盾検出）・不変条件・安全性・活性・デッドロック・到達性の検証
- ✅ 反例の解釈（仕様の欠陥かモデル化ミスかの切り分け）
- ✅ Alloy で表現できなかった/近似した部分の明示

### 含まれないもの
- ❌ 仕様自体の修正（修正提案のみ。確定は人が行う）
- ❌ 実装コードの生成・実装の検証
- ❌ 無限領域での証明（Alloy は有界検査。「scope 内で反例なし」までしか言えない）
- ❌ 精密な算術・実数・文字列・性能に関する検証

---

## 前提: Alloy CLI

`scripts/run_alloy.sh` が CLI を自動解決する（`alloy` → `alloy6` → `$ALLOY_CMD` → `java -jar $ALLOY_JAR`）。見つからなければ利用者に導入を依頼する。
サンドボックスで `/tmp` が書込不可の場合でも、スクリプトが `$TMPDIR` を Java の一時領域に設定する。

構文や時相演算子に迷ったら `references/alloy6-cheatsheet.md`、モデリング方針や検証コマンドの設計は `references/modeling-patterns.md` を読む。

## ワークフロー

### Phase 1: 仕様の把握と抽出
仕様を読み、次を一覧化する。

- エンティティと関係（多重度）
- 静的な制約・不変条件
- 操作（事前条件・事後条件・変化しないもの）
- 状態と遷移、初期状態
- 安全性（悪いことは起きない）と活性（良いことがいつか起きる）の要求

仕様に複数の解釈があるときは、Alloy の結果を左右する点に絞ってユーザーに確認する。確認せず進める場合は「仮定」として記録する。仕様に無い制約を補って矛盾を隠すと検証の意味がなくなるため、補った内容は必ず仮定に残す。

### Phase 2: トレーサビリティ表
仕様項目に ID を振り、Alloy 要素（sig / fact / pred / assert）との対応表を作る。どの仕様項目もどこかに対応するか、対応しない理由（モデル化対象外）を書く。この表が抜け漏れの検出とレポートの根拠になる。

### Phase 3: モデル化
順に書く: 構造（sig・field）→ 静的制約（fact）→ 操作（pred。フレーム条件を含める）→ 振る舞い（`var` と `fact Traces`）。

- 仕様が「規則」として定めるものは fact / pred、「保証したい性質」は assert にする。性質を fact に書くと必ず成立してしまい検証が空転する。
- 状態を持たない仕様（データモデルの整合性のみ）は時相部分を省いてよい。
- 出力先（既定はカレントの `alloy-verification/`）に `model.als` として保存する。ファイル先頭のコメントに仕様項目IDとの対応を書く。

### Phase 4: 検証コマンドの設計
`references/modeling-patterns.md` の「検証コマンドの型」に従い、最低限次を含める。

1. 全 fact の同時充足可能性（`run {}`）
2. 各操作の実行可能性（`run`）
3. 仕様が主張する各性質の `assert` + `check`
4. 状態遷移がある場合はデッドロックと目的状態への到達性

scope は小さく始め、上限のある仕様は上限+1 も試す。

### Phase 5: 実行

```bash
bash <skill-dir>/scripts/run_alloy.sh alloy-verification/model.als
```

構文・型エラーはメッセージに従って修正し再実行する。結果表の読み方:

| コマンド | SAT | UNSAT |
|---|---|---|
| `run` | 例が存在（充足可能） | 充足不能（矛盾・過剰制約・到達不能） |
| `check` | **反例あり**（性質が破れる） | scope 内で反例なし |

### Phase 6: 結果の解釈
期待と異なる結果は、反例（`<出力先>/*-solution-*.txt`）を読んで原因を切り分ける。

- **モデル化ミス**: フレーム条件の欠落、初期状態や `always` の書き漏れ、Int のオーバーフローなど。モデルを直して再実行する。
- **仕様の欠陥**: 要求同士の矛盾、操作の組み合わせによる不変条件違反、未定義の遷移など。反例を「ステップ1: …、ステップ2: …」と仕様の用語で説明し、修正案を添える。

check が全て反例なしのときは、主要な fact を1つ外して反例が出るか（性質が本当にその制約に支えられているか）を確認し、検証の空転を疑う。

### Phase 7: レポート
`alloy-verification/verification-report.md` に次の構成で出力し、要点をユーザーに伝える。

```markdown
# 仕様 Alloy 検証レポート

## 概要
（検証対象、結論を1〜3文。使用した Alloy コマンドと scope）

## 検証結果サマリ
| コマンド | 結果 | 意味 | 関連する仕様項目 |

## 検出された問題
### [重大度] 問題名
- 該当する仕様: 
- 反例（仕様の言葉で）: 
- 原因: 仕様の欠陥 / モデル化ミス（修正済み）
- 修正提案: 

（問題なしの場合はその旨を明記）

## トレーサビリティ
| 仕様項目ID | 内容 | Alloy 要素 | 検証コマンド |

## モデル化で置いた仮定・近似
（補った制約、表現できず省略/近似した仕様項目とその理由）

## 検証の限界
（scope、steps、有界検査であること）
```

問題が無い場合に問題をでっち上げない。逆に、反例が出たのに仮定を足して消すこともしない。
