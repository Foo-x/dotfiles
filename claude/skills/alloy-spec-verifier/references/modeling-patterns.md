# 仕様 → Alloy モデリングパターン

## 対応表
| 仕様の要素 | Alloy での表現 |
|---|---|
| エンティティ / 用語 | `sig`(区別が要るなら `abstract sig` + `extends`、状態なら `enum`) |
| 属性・関連 | field。多重度は仕様の「1件」「任意」「複数」を `one/lone/set/some` に対応 |
| 「〜は一意」 | `fact { all disj a, b: S \| a.key != b.key }` |
| 「常に〜」「〜してはならない」 | `assert` + `check`(`always`)。**仕様が事実として述べている場合のみ** `fact` |
| 「〜のとき〜する」(EARS WHEN) | 操作 `pred` の事前/事後条件 |
| 「〜の間」(EARS WHILE) | 状態を前提にした `always (状態 implies …)` |
| 「〜の場合は〜する」(IF-THEN) | `implies` |
| 「いずれ〜する」 | `eventually`(公平性の前提が必要なことが多い) |
| 数量制限「最大N件」 | `#x <= N`。Int の範囲を超えない bitwidth を設定 |
| 権限・ロール | `Role -> Permission` 関係 + 操作 pred のガード |

## 「fact」と「assert」の使い分け(最重要)
- **仕様が定める規則**(前提・ドメイン制約・操作の意味)は `fact` / `pred` に書く
- **仕様が満たすべきと主張する性質**(不変条件・安全性)は `assert` に書き `check` する
- 性質を `fact` にすると常に成立して見え、検証が空回りする。判断に迷う項目は仕様の文面が「規則の定義」か「結果として保証したいこと」かで分ける

## 検証コマンドの型
1. **健全性チェック(空転防止)**: `run {} for N` で全 fact の組み合わせが充足可能か。UNSAT なら fact 間の矛盾
2. **操作の実行可能性**: 各操作について `run { some x: T | op[x] }`。UNSAT なら到達不能な操作(事前条件が強すぎる、初期状態からたどり着けない)
3. **不変条件 / 安全性**: `assert Inv { always (…) }` + `check`
4. **デッドロック**: `assert NoDeadlock { always (some t: T | canDoAny[t]) }` 相当。stutter を許すモデルでは「stutter 以外の操作が可能」を別 pred で表現する
5. **到達性**: `run { eventually 目的状態 }`。UNSAT なら目的状態に到達できない
6. **活性**: `check { always (要求発生 implies eventually 応答) }`。反例は公平性不足で出やすいので、`fact Fairness` を明示し仮定としてレポートに載せる
7. **ミューテーション確認**: 主要な fact を1つ外して check が SAT(反例)になるか。ならなければ性質がその fact に依存しておらず、検証が弱い

## 反例の判定
- 反例 = 「仕様の欠陥」か「モデル化ミス」かを必ず切り分ける
  - モデル化ミスの典型: フレーム条件の欠落(操作中に無関係な関係が勝手に変わる)、初期状態の制約漏れ、Int オーバーフロー、stutter の許可漏れ/過剰
  - 仕様の欠陥の典型: 2つの要求の同時成立不能、操作の組み合わせで不変条件が破れる、未定義の状態遷移
- 反例トレースは Alloy の atom 名ではなく、仕様の用語で「ステップ1: …、ステップ2: …」と説明する

## scope の扱い
- 小さく始める(3〜4 atoms, 6〜10 steps)。UNSAT/反例なしは「その scope 内では」としか言えない
- 数量制限のある仕様は、上限より大きい scope も試す(上限+1 で違反が起きるか)
- 結果が scope に依存しそうなら scope を上げて再実行し、レポートに検証した scope を記載する

## よくある落とし穴
- `var` を付け忘れると「時間で変わらない」ことになり、操作が UNSAT になる
- 事後条件だけ書いてフレーム条件を書かない → 反例だらけ。`x' = x` を全 var に対して書く
- `fact Traces` に `init` を入れ忘れ、任意の状態から始まる
- `always` を忘れて最初の1ステップだけ遷移条件が課される
- 多重度の既定は `one`。「無い場合もある」は `lone`
- `disj` を書かず同一 atom を2つ別物として扱えていない
- 数値や日付を扱う仕様は Int で近似する。厳密な算術検証には不向き(Alloy の限界としてレポートに記載)
