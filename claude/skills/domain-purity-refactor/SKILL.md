# ドメイン層の純粋化リファクタ

ドメイン層から外部依存を排除し、ユースケース（Application 層）の端へ押し出す。
根拠: Vladimir Khorikov "Domain model purity vs. completeness"（https://enterprisecraftsmanship.com/posts/domain-model-purity-completeness/）。詳細は `references/trilemma.md`。

## 原則

- **純粋性**: ドメインクラスはプリミティブ型と他のドメインクラスにのみ依存する。インターフェース越しのリポジトリ注入やデリゲート渡しも、外部へ問い合わせる点で不純とみなす
- **トリレンマ**: 完全性（ドメインロジックが全てドメイン層にある）・純粋性・パフォーマンスは2つしか満たせない
- **優先順位**: 純粋性 > 完全性。ドメイン層をドメインロジック以外の責務から守る
- 選択肢は次の順に検討する
  1. 外部の読み書きを操作の端に寄せる（read-decide-act）。完全性と純粋性を保てる
  2. ①が使えないとき、外部問い合わせを伴う判断をユースケースへ分割する（完全性を犠牲にする）
  3. ドメインへ依存を注入する案は採らない（純粋性を失う）

## ワークフロー

### 1. スコープ確認
- 対象範囲（全体・ディレクトリ・ファイル）を確認する
- ドメイン層・ユースケース層・アダプタ層のディレクトリを特定する。特定できなければユーザーに確認する

### 2. 不純箇所の検出
ドメイン層で次を探す。

- repository / gateway / client / DB / HTTP / ファイル / キュー / ロガーの参照や import
- それらのインターフェース、デリゲート、コールバックを引数やコンストラクタで受け取るメソッド
- 現在時刻・乱数・UUID生成・環境変数の直接取得
- 遅延ロードされるプロパティ（アクセス時にDBへ問い合わせるもの）
- ドメイン内から起こしている副作用（メール送信、イベント発行、永続化）

### 3. 方針の分類
各箇所を次のとおり分類する。

| 状況 | 方針 |
|---|---|
| 必要なデータを事前に低コストで取得できる | ①ユースケースが取得し、値としてドメインへ渡す。時刻・乱数・IDも引数にする |
| 判断の途中で追加データが要る、または全件取得が非現実的 | ②外部問い合わせを伴う判断（例: メールの一意性）をユースケースへ移す。ドメインには純粋な判断だけを残す |
| ドメインが副作用を起こしている | 決定を返り値またはドメインイベントとして返し、ユースケースが実行する |

②を選んだ場合は、ドメイン側に事前条件や判定メソッド（`canChangeEmail` 等）を用意して、ユースケースが外部確認の結果を渡す形にする。ドメインのメソッドが外部確認を前提にしていることをシグネチャで読み取れるようにする。

### 4. 計画の提示と承認
- 箇所ごとに、現状・分類・変更後のシグネチャを一覧にして提示する
- ユーザーの承認を得てから修正する
- 修正前に `programming-best-practices` スキルを読み込む

### 5. 修正
- 1箇所ずつ変更し、その都度テストを通す
- 純粋化したドメインへ依存する呼び出し側（ユースケース）を合わせて修正する
- 依存方向は常にアダプタ → ユースケース → ドメインを保つ

### 6. テスト更新
- `unit-testing-best-practices` スキルを読み込む
- ドメインのテストからモック・スタブを除き、入力と出力だけを検証するテストにする
- ②でユースケースへ移した判断は、ユースケースのテストで担保する

### 7. 検証
- 既存テスト、ビルド、型チェック、lint を実行する
- ドメイン層に外部依存の import が残っていないことを grep で確認する

## 報告

- 箇所ごとの選択（①②）と理由
- ②で生じた完全性の低下（ユースケースへ移ったビジネスルール）の一覧
- 残った不純箇所と、残した理由

## 禁止事項

- 純粋にするためにリポジトリのインターフェースをドメイン層へ置いたまま渡すこと（依存の向きが変わるだけで不純なまま）
- パフォーマンス対策なしで全件取得して引数に渡すこと
